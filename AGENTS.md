# AGENTS.md — Public Share Control

Nextcloud app. Three features on public folder-share links:
1. Owner-facing sidebar dropdown: pick which "Create new" menu entries (new folder, doc, whiteboard, …) are hidden for visitors of *this specific link*. "Upload from device" is never listed — it can't be hidden.
2. Visitor-facing "Upload files" button, rendered inline in the same toolbar row as "Public share ▾" (not a separate row), at every screen width.
3. (Since 0.5.0) Admin settings panel (Settings → Sharing): instance-wide "hidden by default" and "forbidden" lists for "Create new" entries, plus a single switch for whether the quick-upload button appears at all. See the 0.5.0 gotcha entry below for the full design — it's the most involved thing in this app and worth reading in full before touching any of the three features above.

Target: Nextcloud 34–35 (both tested live). Older versions are deliberately unsupported: the typed `IAppConfig` getters need NC 29, the sidebar extension API NC 31, and nothing below 34 has been tested — don't lower `min-version` without testing that version. Architecture rule from the project owner: **use public `@nextcloud/*` APIs only, never DOM-scraping or internal core classes** — the whole point is that upgrades to future NC versions shouldn't need workarounds.

## Repository history note

## Key architecture decisions / APIs used

- Owner dropdown: `registerSidebarAction()` (`@nextcloud/sharing/ui`) — same mechanism as core's `files_downloadlimit`. Its selection is written in place into `share.attributes` and saved by core's own "Update share" request; `onSave` only marks the state as saved.
- **Position in the sidebar is fixed, not configurable.** `ISidebarAction.order` only sorts registered actions relative to *each other*. `SharingDetailsTab.vue` renders all external actions in one `v-for` at a fixed point (between "Show files in grid view" and "Custom permissions"); no position/slot API exists.
- Entry list: `getNewFileMenuEntries()` called **without** a context argument on the public page (a fake context would trigger every entry's own `enabled(context)`, which can throw on third-party entries expecting a real Node).
- Quick-upload button: `registerFileListAction()` — NOT `registerFileListHeader()` (renders its own separate row; the owner explicitly wanted the same row as "Public share ▾"). That row has `force-name="true"` in core, so the label is always visible, at every width.
- Upload: `getUploader(true).batchUpload()` (`@nextcloud/files/upload`) — the shared global uploader core's own upload UI listens to.
- **Uploader gap**: `batchUpload()` resolves without a usable `Node`, and the file list only refreshes on `files:node:created`. After upload, `getClient().stat()` each file (`@nextcloud/files/dav`), `resultToNode()`, then `emit('files:node:created', node)` — same sequence as core's `TemplatePicker.vue` anonymous-public-share branch. Without this, uploads succeed but don't appear until reload.
- **`batchUpload()` resolves before the uploads finish.** It returns once the uploads are queued — stat-ing right away gets a 404 because the PUT is still running (observed in the network trace: PROPFIND 404, then PUT 201). Wait for each returned `IUpload` to reach a terminal status (its `finished` event fires for FINISHED/CANCELLED/FAILED, status already set). The returned array is `[...one upload per file, one trailing upload for the whole batch]` in no guaranteed file order (read from `upload.mjs`), so the uploaded files are taken from the file uploads themselves (`children.length === 0`), with the final name read from `upload.source` (not URL-encoded) — never matched by index or by the picked file's name.
- **Name conflicts (fixed after review — previously silent overwrites).** Without a `callback`, `batchUpload()` overwrites existing files without asking; core's own upload shows a conflict dialog. `resolveConflicts()` in `quickUploadAction.ts` uses core's own dialog, `openConflictPicker()` (`@nextcloud/dialogs`), through batchUpload's `callback` contract (read from `upload.mjs`): it receives the incoming names and returns `{ incomingName: nameToUploadAs }` — same name overwrites, another name uploads renamed (generated with `getUniqueName()` from `@nextcloud/files`, avoiding existing, incoming and already-generated names), a missing key skips that file, `false` cancels everything. Skipped files are only `cancel()`ed (abort signal) and never start, so they never dispatch `finished` — `waitForUpload()` also resolves on the abort signal, otherwise it would hang. Verified on NC34/35: Cancel keeps the original untouched, "Keep both" adds `name (1).ext`, "Replace" overwrites; every result shows in the list without reload and without duplicate rows.
- Filtered-out core entries in the dropdown: `file-request` and `template-picker` — both can never apply to an anonymous visitor. See `NEVER_PUBLIC_ENTRY_IDS`.
- **Which entries are controllable:** `isControllableEntry()` in `hiddenEntries.ts` — categories `CreateNew` (1) **and** `Other` (2); `UploadFromDevice` (0) never. Used by both the sidebar list and `public.ts`, so the two can't disagree. `Other` was added for the Text app's **"Add folder description"** (id `rich-workspace-init`, creates a `Readme.md` shown above the file list), which registers itself in that category — confirmed by dumping the registry on NC34 and NC35, where it is visible to public-link visitors.

## Gotchas (don't re-discover these)

- **Forgetting `Util::addStyle()`** (only calling `addScript()`) → completely unstyled UI. Always pair them.
- **`NcCheckboxRadioSwitch`'s `#icon` slot replaces the checked/unchecked glyph** instead of adding alongside it. Put the icon in the **default** slot next to the label.
- **`title` on `NcCheckboxRadioSwitch` never shows as a tooltip**: the component passes it on to its visually hidden `<input>` (disabled for forbidden entries), which never receives the pointer. Put the `title` on a wrapper element around the switch — browsers show the title of the nearest ancestor under the pointer. Native `title` is the Nextcloud way here (`@nextcloud/vue` 9 has no tooltip component/directive). Covered by the forbidden-entry e2e test via `elementFromPoint()`, since native tooltips can't be screenshotted.
- **`BeforeTemplateRenderedEvent` also fires on the password page** of protected links (`showAuthenticate()`, `showAuthFailed()`, `showIdentificationResult()` in core's `ShareController`, scope `SCOPE_PUBLIC_SHARE_AUTH`) — before the visitor has authenticated. Up to 0.5.0 the listener ignored the scope and put the link's selection, the admin lists and its script on that page. It now acts only when `getScope()` is `null` (the share page itself) — a positive check, so scopes core adds later are ignored too. Covered by `tests/e2e/password.spec.ts`.
- **SVG icons from other apps** (`iconSvgInline` of "New" menu entries and template creators) are rendered with `NcIconSvgWrapper`, which sanitizes them with DOMPurify — never with `v-html`. That's how core renders the same icons.
- **Styling: no overrides of `@nextcloud/vue` internals.** No `!important`, no restyling of component parts — use the components' props instead (e.g. `NcButton`'s `wide` + `alignment="start"` for the popover's "Select all"). Spacing via `--default-grid-baseline` multiples, small text via `--font-size-small`, colours only via theme variables (dark mode then works as is; checked on NC35).
- **No uninstall repair step, on purpose.** Nextcloud runs an app's `uninstall` repair steps on every *disable* too (`AppManager::disableApp()`), so deleting the admin settings there would wipe them on a temporary disable. What remains after removal (the per-link attribute, four app config values) has no effect without the app — verified on NC34: public page clean, no log errors, shares still editable — and is documented in the README's "Uninstalling" section.
- **Listing every entry on the admin page (discovery).** Entries registered only in the browser can't be enumerated anywhere but in the Files app, so `src/discovery.ts` reports them from an admin's Files app to `DiscoveredEntriesController`. Template-based entries are left out (the server lists them; their ids aren't stable anyway), as are `NEVER_PUBLIC_ENTRY_IDS`. Nothing is sent while the registered list equals the stored one (pushed as initial state, admins only). New or changed entries are sent right away, merged with stored entries not registered (yet), since apps may register late (`registerEntry()` is wrapped, as on the public page). Entries still missing when the page is left (`pagehide`, `keepalive` request) are gone and removed then — no timers anywhere. **One request at a time:** in CI an older addition request overtook the removal sent on leaving and restored the removed entry. Changes made while a request runs are sent once it's done; a removal due while a request runs waits for a later visit. Labels are in the discovering admin's language. Stored as lazy app config (`discovered-entries`), so it's only loaded where read. Entries an app registers *only* on public pages can't be discovered.
- **Apps registering the same entry under different ids (OnlyOffice).** OnlyOffice registers its document/spreadsheet/presentation creators as templates only for signed-in users (`isUserAllowedToUse()`: "no user -> no"), so the Files app lists them as `template-new-onlyoffice-<n>`, while on public pages its own script adds `new-onlyoffice-docx`/`-xlsx`/`-pptx` instead. Nothing links the two but the icon, which is byte-identical in both contexts (verified for every entry on NC35 with OnlyOffice 10.2.1). Hence the icon fingerprint (`iconFingerprint()`, FNV-1a 64 bit) stored with each entry — but only when the icon is unique among the listed entries (`uniqueIconHashes()`), so equal icons never link anything. Entries stored before fingerprints existed keep the old displayName fallback, which only works when owner and visitor use the same language; re-saving adds the fingerprint. The matching logic is covered by unit tests; the behavior with the real OnlyOffice app was verified by hand on NC35 (admin restriction and owner selection, English and German visitors). To re-check it, install OnlyOffice on a test instance: make `custom_apps` writable (`chown www-data:www-data`, Docker creates the mount point as root), `occ app:install onlyoffice`, set `DocumentServerUrl` to any URL (it needn't be reachable; without one OnlyOffice loads no menu scripts), restart the container — and remove it again afterwards, so the instances match CI.
- **New routes need a cache flush on the local instances.** Nextcloud caches an app's routes per app version; a controller added without a version bump answers 404 until the instances restart (`docker restart pscontrol-nc34 pscontrol-nc35`). Real updates and CI (fresh instances) aren't affected.
- **No quick-upload button on upload-only links (file requests).** There are two kinds, both create-only and shown with Nextcloud's own central upload button: "File request" in the share menu (permissions only) and "+ New → Create file request" (additionally the attribute `fileRequest`/`enabled`). For the latter, the server rejects every upload without an `X-NC-Nickname` header ("A nickname header is required for file requests", `FilesDropPlugin`), which only Nextcloud's own upload page asks for; without read permission our button couldn't list the uploads either. `BeforeTemplateRenderedListener` therefore pushes the quick-upload flag as off for links without read permission or with that attribute (same check as core). Both kinds are covered in `quick-upload.spec.ts`.
- Raw SQL test writes to `oc_share.attributes` must use the real serialization shape `[["scope","key",value], ...]` (indexed arrays), not objects — the wrong shape 500s every page load for that share.
- `info.xml`'s `max-version` blocks activation on newer NC — bump it deliberately.
- App was renamed `share_no_new` → `public_share_control`. Anything still saying `share_no_new`/`ShareNoNew` is stale.
- **Save mechanism — read before touching it.** History: a whole-`share`-object watcher reset in-progress edits (fixed in 0.3.1 by keying on `'share.id'`); a separate "Save" button (0.4.0) was reverted in 0.4.1; then a second PUT of our own after core's, plus a session cache (0.4.4). **That two-request design lost data** (found in review, reproduced on NC34/35): core's PUT sends its in-memory `attributes`, which never contained our latest value, so saving any *other* setting later without a reload overwrote the owner's selection on the server, while the session cache kept showing the old one.
  - **Current design (verified on NC34/35, core source read on stable34):** core's `SidebarTabExternalAction.vue` passes `toRaw(props.share)` — in core's Vue 2.7 that is core's actual `Share` model instance. Its `attributes` is a **getter without setter** returning the live array (`_share.attributes`, always an array after construction). Core edits that array in place itself (`set hideDownload`) and `SharesMixin.queueUpdate()` sends `JSON.stringify(this.share.attributes)` without replacing the object afterwards. So `writeOwnAttribute()` edits that array in place (splice/push) on every checkbox change, and core's single "Update share" request saves it. The earlier "direct mutation doesn't work" finding was almost certainly an **assignment** to the setter-less getter — never assign `share.attributes = …`.
  - Mirrors core's own field handling: core edits label/note/hideDownload in place and its `cancel()` restores captured initial values. Likewise, `markSaved()` (via `onSave`, which core calls after its request) records the saved state, and `beforeUnmount` restores the saved attribute if the editor closes without saving. Toggling back to the saved selection restores the saved attribute exactly — including "no attribute", so an untouched share keeps following the admin defaults.
  - Tests that cover it: one PUT per save; selection survives a later save of another setting without reload; Cancel discards; toggle-and-back writes nothing; full reload shows the saved state.
- Verification recipe for sidebar save bugs: reset the share's `attributes` to `NULL`, change the selection, click the real "Update share" button, do a **full page navigation** back, reopen sidebar → Advanced settings and check the "N of M hidden" label, then load the public link in a **fresh, unauthenticated** browser context and check the "+" menu. The first two can silently diverge.
- **Late-registering "Create new" entries.** `NewMenu` has no "entry registered" event. 0.4.1 used time-based retries (rejected by the owner as guessing). Since 0.4.2, `watchForLateRegistrations()` wraps the singleton's `registerEntry()` (obtained via the public `getNewFileMenu()`) and reverses matching registrations instantly.
- **Template-based entry ids are not stable across page loads (root-caused in 0.4.3).** Core's `registerTemplateEntries()` (`apps/files/src/newMenu/newFromTemplate.ts`) builds ids as `` `template-new-${provider.app}-${index}` `` from `loadState('files' | 'files_sharing', 'templates', [])`, with `index` being an array position. Server-side that list comes from `TemplateManager::listCreators()`, sorted by `getOrder()` (default 100 for most) with ties broken by registration order — no contractual ordering anywhere. `displayName` is translated, so it's no safe fallback either. Fix: `templateKeyFor()` re-reads the same `templates` initial state (memoized, safe to read twice) and maps the current id to `<app>:<extension>` — intrinsic, untranslated. Matching tries templateKey → id → icon fingerprint → displayName (only for entries stored without a fingerprint; see the OnlyOffice gotcha). **If core ever changes the shape of `templates` or the id format, this must be re-derived from source.** Such a change fails open (entries stay visible) and is made visible: the sidebar logs a console warning when no rebuilt id matches a registered entry (`templateIdFormatMatches()`), and the e2e test "core's template entry id format still matches" fails. `app:extension` only needs to be unique within one app (app ids are globally unique).
- **Instance-wide admin defaults/restrictions (0.5.0).**
  - Server-side enumeration exists **only** for template-based entries (`ITemplateManager::listCreators()`, safe from any PHP context). Every other entry ("New folder", the Text app's "Add folder description", OnlyOffice's "New PDF form", any app's `addNewFileMenuEntry()`) exists only in the browser; the admin page lists them from the discovered entries (see "Listing every entry on the admin page").
  - **Explicit vs. never-touched.** Before 0.5.0, `save()` omitted the attribute for an empty selection, so "explicitly show everything" and "never touched" were identical in storage. Fixed by persisting the attribute whenever the owner changes the selection (even `[]`), pushing it from `BeforeTemplateRenderedListener.php` whenever it exists, and reading it with a `null` sentinel in `public.ts`. `ShareAttributes::getAttribute()` already distinguishes `null` from `[]`. Known one-time side effect: a share explicitly saved as "show everything" before 0.5.0 is indistinguishable from an untouched one, so it picks up newly configured default-hidden entries until its owner saves it once more — affects only "Hidden by default", never "Forbidden". A possible fix (only apply defaults to shares whose `share.createdTime` is after the moment defaults were first configured) was designed but not implemented — `createdTime` is available on the sidebar's `share` prop and as `$share->getShareTime()` server-side.
  - **Merge model**: `effectiveHidden = forbidden ∪ (explicit ?? default)`. Forbidden is evaluated fresh on every page load, so it applies to existing links immediately. An explicit per-share choice fully replaces the default.
  - New entries from apps installed later are visible by default: every list is a "what to hide" list, so anything unlisted stays visible.
  - Forbidden entries are filtered out of what `save()` persists per share — enforced at read time instead, so an admin un-forbid takes effect immediately.
  - Admin config lists reuse the `HiddenEntryRef[]` shape; `matchesHiddenEntry()` needed no changes. `AdminSettings.vue` builds `<app>:<extension>` keys directly from `listCreators()` output (no volatile ids exist there); template rows are stored as `{ id: templateKey, templateKey }`, "New folder" as `{ id: 'newFolder' }`.
  - Admin page is plain `ISettings` (a full admin passes `AppConfigController::isAllowedToChangedKey()` unconditionally). The provisioning_api endpoint has `#[PasswordConfirmationRequired]`, hence `confirmPassword()` from `@nextcloud/password-confirmation` before every save.
  - **Admin page saving** (`AdminSettings.vue`): every change saves immediately; entry-list saves never overlap (`saveEntries()` loops while changes arrive during a save, then saves the newest state) because both lists are shared array-valued keys and overlapping requests could land out of order. On failure — including a cancelled password confirmation — switches revert to the last server-confirmed state (`savedDefaultHiddenKeys`/`savedForbiddenKeys`) and an error is shown; the quick-upload switch shows a loading state and reverts the same way. Configured entries without a row on the page (e.g. from a currently disabled app) are kept on save (`storedRefs`), not silently dropped. An earlier 500 ms debounce was removed: it lost changes when leaving the page quickly.
  - Writes via the generic endpoint without a lexicon entry land as `setValueMixed()`; reading `VALUE_MIXED` with any typed getter is safe (`getTypedValue()` skips the type-conflict check for mixed).

## Build / test workflow

```bash
npm ci
npm run build              # → js/public_share_control-{main,public,settings}.mjs (+ shared chunks), css/…
npm run lint               # needs Node ≥ 22.14 (@nextcloud/eslint-config uses module.findPackageJSON);
                           # on an older local Node: npx -y node@22 node_modules/eslint/bin/eslint.js
npm run test:unit          # vitest: matching logic in src/hiddenEntries.ts (tests/unit/)
npm run test:e2e           # playwright against dev/compose.yaml instances (tests/e2e/), see below
composer install           # incl. dev tools: nextcloud/ocp (types), nextcloud/coding-standard, psalm
composer cs:check          # Nextcloud PHP code style (cs:fix to apply)
composer psalm             # static analysis, errorLevel 1 — needs PHP ≥ 8.3.16 (see below)
composer lint              # php -l on all app PHP files
```

`package.json` declares Node 24; build and unit tests also run on Node 20.17, linting does not. The release package is built by `scripts/package.sh` (see "Releasing").

Psalm on an older local PHP: run it inside a test container, where the repo is mounted — `docker exec -w /var/www/html/custom_apps/public_share_control pscontrol-nc34 php vendor/bin/psalm.phar --threads=1 --no-cache`. Event classes from the bundled `files`/`files_sharing` apps aren't in `nextcloud/ocp`; `tests/stubs/oca_files_events.php` stubs them (signatures copied from NC34). Classes are `final` and interface methods carry `#[\Override]`, as psalm level 1 and Nextcloud's own code require.

### Local test instances (NC34 + NC35)

```bash
docker compose -f dev/compose.yaml up -d   # nextcloud:34 on :8034, nextcloud:35 on :8035 (SQLite)
dev/setup.sh                               # waits for install, enables the app, creates PSC-Test + public link, prints URLs
```

Admin login on both: `admin` / `Admin1234!` — public in this repository, which is why both instances listen on `127.0.0.1` only. The repo is bind-mounted read-only as `custom_apps/public_share_control`, so `npm run build` takes effect on the next page load — no copying. `occ`: `docker exec -u www-data pscontrol-nc34 php occ …`. Tear down with `docker compose -f dev/compose.yaml down -v` (`-v` also deletes the instances' data).

After a version bump in `info.xml` (every release and pre-release), Nextcloud answers 503 on the instances until `occ upgrade` has run; `dev/setup.sh` and the e2e global setup run it.

`dev/setup.sh` also disables `firstrunwizard` — on NC35 its "Welcome" dialog overlays the Files app and blocks clicks (Escape doesn't close it).

**`occ config:app:set` does not reach the web server right away** on these instances: app config is cached in APCu, which the CLI doesn't share, so the web server keeps serving the old value until its cache expires. Change app config through the web server instead — the provisioning API endpoint the admin page uses (`POST/DELETE /ocs/v2.php/apps/provisioning_api/api/v1/config/apps/public_share_control/<key>` with admin Basic auth); the e2e helpers do exactly that.

### End-to-end tests

`tests/e2e/` covers every behavior verified by hand so far, on both instances (`projects` in `playwright.config.ts`): sidebar listing, hiding for visitors, single-request saving that survives later saves, cancel, toggle-back, reload; quick upload incl. all three conflict choices and read-only links; password-protected links (nothing from the app on the password page, everything as usual after it); admin icons, forbidden, default-hidden + owner override, quick-upload switch, failed-save revert; discovery (listing after a Files visit, removal on leaving, admin-only, CSRF, invalid lists); and the template-id-format guard. Each spec uses its own folder (`PSC-E2E-*`) and resets admin config after each test. Tests run serially (shared server state).

First run needs a browser: `npx playwright install chromium`, or point `PSC_CHROMIUM_PATH` at an existing Chromium. Labels are English (global setup sets the admin's language). File names in the list are split into basename/extension spans — match rows via `[data-cy-files-list-row-name="…"]`.

### Screenshots

`screenshots/*.png` (referenced by `info.xml`, i.e. shown in the app store and in Nextcloud's app management) are taken by `npm run screenshots` on the NC35 instance — `dev/screenshots.spec.ts` with its own config, so the e2e suite never runs it. Raise `max-version` in `info.xml` only after adding a project for the new version (new service in `dev/compose.yaml` + entry in `playwright.config.ts`) and seeing it pass.

## Releasing

Changes go under `## [Unreleased]` in `CHANGELOG.md` as they are made. A release is a pushed tag `vX.Y.Z`; commits to `main` without a tag only run CI.

```bash
scripts/bump-version.sh 1.2.0      # info.xml, package.json(+lock); "## [Unreleased]" → "## [1.2.0]" plus a new empty "## [Unreleased]" above
git commit -am "Release 1.2.0" && git push   # wait for CI to be green
git tag -a v1.2.0 -m "Public Share Control 1.2.0" && git push origin v1.2.0
```

**Pre-releases** for testing before a final release: `scripts/bump-version.sh 1.2.0-beta.1` (`alpha`, `beta` or `rc`, numbered), then commit, push and tag `v1.2.0-beta.1` the same way. The CHANGELOG stays untouched — a pre-release's notes are the current `## [Unreleased]` section, which is also where the app store reads them from — and the GitHub release is marked "Pre-release". Further pre-releases (`-beta.2`, `-rc.1`) and finally `1.2.0` follow the same way. `bump-version.sh` refuses any version that isn't newer than every existing `v*` tag, compared with PHP's `version_compare()` like Nextcloud does (`1.2.0-beta.1` < `1.2.0-rc.1` < `1.2.0`) — so a broken pre-release is fixed with the next one, never by going back.

The tag triggers `.github/workflows/release.yml`: it refuses tags whose version differs from `info.xml`/`package.json` or that have no CHANGELOG section, runs the complete CI (`ci.yml`, incl. e2e on NC34+35) and then publishes a GitHub release with `public_share_control-<version>.tar.gz` attached (also kept as a workflow artifact); the release notes are that version's CHANGELOG section (`scripts/release-notes.sh`).

`scripts/package.sh` packages an explicit allowlist — `appinfo`, `lib`, `templates`, `l10n`, `img`, built `js`/`css` (incl. `.license` files, without source maps), `LICENSE`, `CHANGELOG.md` (the app store reads release notes from the package; `README.md` is not shipped — nothing reads it at runtime) — reproducibly (sorted, fixed owner and file modes, commit mtime): a local `scripts/package.sh` on the tagged commit produces the release asset byte for byte (verified for 1.0.0-beta.2; without fixed modes the local umask made the archives differ). **No `vendor/`:** Nextcloud never loads it (`OC_App::registerAutoloading()` only loads `composer/autoload.php` and otherwise maps the app namespace to `lib/` itself) and the app has no PHP runtime dependencies; the local `vendor/` only holds dev tools. Verified by installing the tarball into a fresh NC34 container (no bind mount) and running the full e2e suite against it.

## Dependency updates

Renovate (`renovate.json`; the Renovate GitHub app is installed on the repository) opens pull requests only, no issues: every Monday morning one PR with all minor/patch updates, one PR per major update and one for lock-file maintenance; security fixes right away. New releases must be 4 days old first. Closing a major-update PR without merging makes Renovate skip that major.

**Version limits that come from Nextcloud, not from the packages themselves, are explicit rules in `renovate.json`** (each with a `description`), because Renovate can't see them:
- `nextcloud/ocp` stays at the `min-version` major; the `nextcloud` Docker images are the test matrix and change only deliberately.
- `vite` stays below 8: `@nextcloud/vite-config` 2.x only accepts vite 7 as a peer dependency, so the vite 8 PR failed with `ERESOLVE` before the lock file could even be written. vite 8 needs `@nextcloud/vite-config` 3 (beta as of October 2026). Majors of both are grouped into one "vite" PR: when it shows up for `@nextcloud/vite-config` 3 and fails, raise `allowedVersions` for vite in that same PR.
- Use the same pattern (`allowedVersions` plus a group) whenever a Nextcloud package doesn't support a new major of something yet.

## AI assistance

This project follows Nextcloud's [AI Contribution Policy](https://github.com/nextcloud/.github/blob/master/AI_POLICY.md). It is binding for contributions to repositories in the Nextcloud GitHub organization, such as the app certificate request, and applied here voluntarily:
- Every commit with AI-assisted content ends with the trailer `Assisted-by: AGENT_NAME:MODEL_VERSION`, e.g. `Assisted-by: ClaudeCode:claude-opus-5-5`. Agents never add `Signed-off-by`.
- Issues, PR descriptions and review comments, here and in Nextcloud's repositories, are written by the maintainer in their own words. Agents don't open issues or PRs.
- Code comments describe the code (behavior, constraints the code can't express), never its history or how it came about; that belongs in commit messages, the CHANGELOG or this file. Keep them brief.
- The maintainer reviews every change and must be able to explain it, especially dependencies, access control and anything security-related, and tests new features on a live instance in every context they reach (signed-in Files app, public links, password-protected links).
